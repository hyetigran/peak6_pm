# Governance recovery: a one-shot `reset_governance` gated on the upgrade authority

**Status:** accepted (devnet, 2026-08-24). Supersedes nothing; executes the
escape hatch GOVERNANCE.md §2 already names.

**Context.** The devnet Config (`HoviJo4x…`, program `HiREME…`) was
initialized with a governance key (`3UMRb…`, also pause + override) and an
operator key (`A6uh…`) that were generated by the seed script and never
persisted (fixed afterwards by `f4b0e84`: every authority is now written to
`keys/<role>-<pubkey>.json`). Both keypairs are lost. Per ADR-0024 only
`governance` may `propose_role`, so every Config role is unreachable:
no market creation, no override settlement, no pause. The 34 markets seeded
2026-08-22 carry a Saturday `close_ts`, so the strict build's
`finalize_settlement_normal` can never pass and only the (lost) override key
can settle them — stranding ≈34 × 1.9 SOL of OpenBook venue rent behind
`close_venue`.

GOVERNANCE.md §2 anticipates exactly this: "Config governance is stuck until
a **program upgrade** (separate plane) ships a migration." We hold the
upgrade authority (`4XT7…`, the local CLI wallet).

**Options.**
1. **New program ID.** Fresh deploy + `initialize_config`. Clean, but
   orphans the deployment (frontend, Railway, docs, seeded markets) and
   permanently strands the venue rent. ~4.8 SOL of program rent is
   recoverable by closing the old program; the ~64 SOL in venues is not.
2. **Migration upgrade (chosen).** A `reset_governance(new_governance)`
   instruction whose only authorization is the program's own upgrade
   authority, proven on-chain by reading this program's `ProgramData`
   account (`program.programdata_address() == program_data.key()` and
   `program_data.upgrade_authority_address == Some(signer)`). Deployed in a
   `--features governance-recovery` build, executed once, then removed by
   redeploying the strict build without the feature.

**Decision.** Option 2. Rationale:
- It is the documented recovery path, and running it on devnet is the
  rehearsal we want before the M6 multisig question (GOVERNANCE.md §5).
- It preserves the deployment identity and reclaims the venue rent, which on
  devnet is the difference between a funded operator and a rate-limited
  faucet.
- Blast radius is bounded: the instruction writes exactly one field
  (`governance`) and clears `pending_governance`. Operator / pause /
  override are NOT touched — the recovered governance rotates them through
  the normal two-step path (ADR-0024), so the audit trail for those roles is
  the ordinary `RoleRotationProposed/Accepted` events.
- The feature gate makes "one-shot" enforceable rather than aspirational:
  the instruction does not exist in the discriminator table of any build we
  intend to leave deployed.

**Why the upgrade authority and not anything else.** Every other candidate
signer is either lost (governance, override, operator) or would create a
new standing backdoor (a hard-coded pubkey, a Config field). The upgrade
authority already has total power over the program (it could ship any
migration), so gating on it adds no new trust assumption — it only makes
the specific migration explicit, evented (`GovernanceReset { previous,
new_governance, upgrade_authority }`), and auditable.

**Consequences.**
- GOVERNANCE.md §1's separation ("Config governance cannot upgrade the
  program"; upgrade authority is not a Config role) holds outside the
  recovery window. Inside it, the upgrade plane writes Config once. This is
  acceptable on devnet and would require the M6 multisig as the upgrade
  authority on mainnet.
- Procedure (all from the machine holding `4XT7…`):
  1. `solana-keygen new -o keys/governance-<pubkey>.json` — back it up
     **before** step 3 (memory rule: never-overwrite-private-keys).
  2. `cargo build-sbf --manifest-path programs/meridian/Cargo.toml --features governance-recovery`
     → `solana program deploy` (extend first if larger).
  3. Send `reset_governance(new_governance)` with accounts
     `[upgrade_authority=4XT7 (signer), program=HiREME…, program_data=yFNgqc…, config]`.
     Verify `GovernanceReset` in the tx logs and `config.governance` on-chain.
  4. New governance: `propose_role(Operator | PauseAuthority | OverrideAuthority)`
     → each new key `accept_role`; persist each under `keys/`.
  5. `make build-devnet` (no feature) → `solana program deploy`. Confirm the
     `reset_governance` discriminator now fails with
     `InstructionFallbackNotFound`.
  6. Override-settle the Saturday-close markets; `prune_venue_orders` /
     `close_venue` recycles the venue rent to the operator (ADR-0027).
- Follow-ups: seed script must refuse to run unless every generated
  authority is on disk (done, `f4b0e84`); record the recovery in
  `DEPLOYMENT.md` and the deployment manifest.
