# Deploy an immutable byte-identical OpenBook copy

**INVALIDATED by M0 evidence (2026-08-20):** v1.7's compiled-in `declare_id` check means the byte-identical artifact cannot execute at any other program ID, and a binary patch cannot be proven complete (`docs/adr/openbook-v2-pin.md` §7). The deployed copy is inert. Superseding decision pending.

G1 verification (`docs/adr/openbook-v2-pin.md`) proved the canonical devnet OpenBook V2 deployment runs exactly the official v1.7 artifact but retains a live external upgrade authority — a non-waiverable G1 failure, since the pinned bytes can be replaced at any time by a key Meridian does not control. V1 therefore deploys its own copy of the verified `openbook_v2-v1.7.so` artifact (SHA-256 `a3eb0fad20778b31a20c6b98e4e61b8e9425ccbfb27a96f8165f70c0381bafa8`, tag `v1.7`, commit `796a470033bc556c1d1a1f76709394fc50c63bf7`) to devnet as a **finalized, immutable** program: upgrade authority `None`, program ID `923gYkFCtTtrL9pX7vQNKR7QJchb2jpY3s26xiWuDxz4`. This is not a fork — the binary is byte-identical and no source is modified — but it abandons the canonical program ID, so Meridian's Venue Markets do not live on the ecosystem's shared OpenBook instance and all OpenBook-derived addresses derive from the Meridian copy. G1's identity requirements now bind to the Meridian deployment: `initialize_config` stores its program ID, ProgramData address, deployment slot, and executable hash, and every CPI re-verifies them. The canonical deployment's ProgramData may differ in on-chain data length (padding); hash comparison follows the truncation rules in the pin evidence file. G2–G10 measurements must run against the Meridian copy. The deploy keypair is disposable after finalization and is never committed; the deployment is re-executable from the release artifact alone, and any redeploy after a devnet reset must re-run the full G1 verification and update the pin evidence file.
